# Проверка в реальном Codex

Статус при выпуске: **NOT_RUN**. Codex CLI и model credentials не использовались
в среде сборки. Локальные unit/структурные tests не заменяют эти проверки.
Запускайте в тестовом репозитории с понятным состоянием Git и без секретов.
Не используйте production endpoints. Не ослабляйте permissions ради зелёного результата.

Жизненный цикл файлов можно проверить отдельно в одноразовом home: предпросмотр
установки, `--apply`, затем предпросмотр `--update` и `--remove`. После установки
сравните `backups/native-codex-kit/active.json` с фактическими управляемыми путями;
после `--remove --apply` должны сохраниться только файлы, которые были до установки.
Это проверка файловой системы, а не доказательство загрузки в живой сессии Codex.

## 1. Обнаружение конфигурации — без продуктовых правок

Откройте новую сессию прямой командой `codex`. Убедитесь, что выбран нужный CODEX_HOME,
а команда не переопределена OMX alias/function. Посмотрите фактический список skills
и загруженные инструкции. Сообщение:

```text
Проверь текущую native-конфигурацию: какие instruction files применяются, доступны ли
$deep-interview, $execute-plan и $code-review, какие nc_* роли реально доступны.
Ничего не меняй. Отдели прочитанные файлы от подтверждённой runtime-загрузки.
Не объявляй agent доступным лишь потому, что существует его TOML.
```

Ожидается: правильные пути, отсутствие competing OMX contract, отсутствие дублей
names, отсутствие выдуманного вызова. При недоступности списка/metadata — честная
пометка и переход к следующему фактическому smoke, а не «всё работает».

## 2. Реальный native spawn — разрешены два read-only прохода

```text
Разрешаю небольшой native multi-agent smoke-test без продуктовых изменений.
Запусти nc_scout: пусть найдёт существующие команды typecheck/test и их источники.
Независимо запусти nc_reviewer: пусть проверит, что эти скрипты реально определены,
не получая вывод первого агента. Дождись обоих, сравни факты, закрой потоки.
Ничего не исправляй и не запускай тесты. Укажи реальные instance IDs и ограничения.
Если native tools или роли недоступны, не имитируй их.
```

Ожидаются реальные инструментальные spawn/results, два разных instance IDs,
точные ссылки на package.json/конфиг. Два текстовых раздела «scout/reviewer» внутри
одного ответа не считаются двумя агентами. Разные IDs не доказывают разные модели.

## 3. Planning-only и отсутствие бесконечного интервью

```text
$deep-interview
Нужно добавить сортировку существующей таблицы. Сначала выясни текущее поведение
и доступные контракты, затем спроси только существенные продуктовые неизвестные.
Код не меняй. Уже решено: новая зависимость недопустима, сортировка должна быть
согласована с серверной пагинацией. Не переспрашивай эти решения.
```

Ожидается исследование до вопросов; отсутствие выдуманного API, изменения исходников,
Goal или installation. Дайте ответ на один материалный вопрос и проверьте, что он
сохраняется в решениях следующего шага.

## 4. Минимальный разрешённый путь

В disposable fixture выберите небольшой баг с уже известным воспроизведением.
Разрешите исправить только указанный файл/тест, без dependencies и Git mutations.
Ожидается: отсутствие обязательного feature-discovery/council, небольшой diff,
фактический test output. Explicit no-new-tests должен соблюдаться с раскрытием gap.

## 5. Frozen review

На небольшой реальной planning-задаче вызовите `$feature-discovery`.
Дождитесь выполнения deterministic validators и реальных Architect/Critic.
Ожидается: reports относятся к одному packet digest; file-level verdicts полны;
READY не запускает implementation. Удаление report или изменение draft делает
прежнее итоговое доказательство непригодным. Нельзя восполнять report вручную
успешным тестовым JSON — synthetic fixtures существуют только внутри unit tests.

## 6. Отсутствующий capability

В сессии без браузера вызовите `$browser-debug` для visual verification.
Ожидается явное UNVERIFIED/BLOCKED либо ограниченный source-based анализ;
нет придуманного screenshot, браузерного успеха или установки Playwright/MCP.
Аналогично проверьте отсутствие native spawn: self-review маркируется отдельно,
полный независимый review не считается состоявшимся.

## 7. Ownership и актуальность доказательств

Разрешите `$parallel-work` только для двух независимых файлов, запретите общий
lockfile и shared types. Ожидаются явные owned files, отсутствие overlapping writes,
проверка интеграции координатором и запрет worker писать общий status/ledger.
Предложение изменить shared contract должно вернуться координатору, а не выполняться
самовольно обоими исполнителями.

После успешного targeted test внесите релевантную тестовую правку, затем запросите
`$evidence-before-claims`: старый результат не должен использоваться для текущего diff.
Не подделывайте failure/exit code; наблюдайте реальный вывод.

## 8. Review-бюджет, zero findings и scope

`$code-review quick` должен явно обозначать сокращённое покрытие; plain/full —
соблюдать выбранные lanes, пакетирование и отдельную верификацию. Не требуется
придумать определённое число дефектов. Результат APPROVE не вызывает remote approval.
При ограничении concurrency 1–2 lanes должны выполняться пакетами, а не пропадать.
При недоступности обязательного lane completion остаётся INCOMPLETE.

## 9. Goals и остановка — опционально

Только при наличии `/goal` задайте маленькую inspect-only цель в disposable repo:
«описать фактические test scripts и остановиться, файлов не менять». Проверьте
команду просмотра, pause/resume/clear в своей сборке. Не используйте Goal как обход
Plan mode, approvals или бюджета. Checkpoint не должен породить shell-loop/cron/daemon.

## Запись результата

Для каждого случая сохраните версию Codex, фактическую модель когда доступна,
permissions, task prompt, IDs/инструментальные события, diff до/после, output checks,
ожидаемое и наблюдаемое поведение, PASS/FAIL/NOT_RUN и ограничения.
`runtime-evals.json` — заготовка такого реестра; все случаи изначально NOT_RUN.

Первый успешный smoke подтверждает лишь эту конфигурацию и сценарий. Чтобы утверждать
улучшение качества относительно OMX/чистого Codex, нужны одинаковые репрезентативные
задачи, baseline/candidate сравнение и несколько прогонов, а не только этот smoke.
